4   THE PROPOSED SOLUTION

4.1   Overall System Architecture

The proposed system is a software simulation framework designed to generate labelled sensor data for the purpose of evaluating LiDAR–camera fusion perception models in an indoor warehouse environment. The system is decomposed into four loosely coupled subsystems: the Simulation subsystem, the Perception subsystem, the Navigation subsystem, and the Training subsystem. At runtime the first three subsystems run concurrently inside a single Python process; the Training subsystem is executed offline after data collection is complete.

Figure 4.1 shows the top-level data-flow between the four subsystems. The Simulation subsystem is the ground truth provider: it maintains the physics state of the warehouse world and exposes the robot body to sensor queries. The Perception subsystem reads raw sensor data from the simulation, produces point clouds and images with ground-truth semantic labels, and optionally persists them to disk. The Navigation subsystem reads the robot pose from the simulation and the list of detected dynamic obstacles from the Perception subsystem, computes kinodynamically feasible paths, and issues velocity commands back to the simulation. The Training subsystem consumes the dataset produced by the Perception subsystem offline; it trains the VirConvNet model and produces a trained checkpoint together with per-class evaluation metrics.

[Figure 4.1 – Top-level system data-flow diagram]
Simulation subsystem ← Navigation commands; Simulation subsystem → Robot pose, Sensor rays
Perception subsystem ← Sensor rays; Perception subsystem → Obstacle list, Dataset (disk)
Navigation subsystem ← Robot pose, Obstacle list; Navigation subsystem → Velocity commands
Training subsystem ← Dataset (disk); Training subsystem → Trained model checkpoint

The architectural decomposition was driven by three design decisions made early in the project:

  1. Separation of sensing and acting. Placing perception and navigation in distinct modules ensures that the LiDAR data pipeline can be toggled on or off without affecting the robot's ability to traverse the warehouse, which simplifies debugging and allows data collection to be enabled selectively.
  2. Oracle localisation. Because the research question concerns perception transfer and not SLAM, the robot pose is taken directly from the PyBullet rigid-body state. This eliminates pose-estimation error from the perception evaluation and removes a large external dependency. A real-world deployment would replace this oracle with a LiDAR-SLAM front-end such as LIO-SAM.
  3. Offline training. Decoupling data collection from model training means the simulation does not need to run at GPU speed, and the training pipeline can be executed on a separate machine (e.g., a cloud GPU instance) without modifying the simulation codebase.

The process by which the architecture was finalised went through two iterations. In the first iteration, the LiDAR sensor was polled synchronously on every physics step, causing the simulation to drop below real-time speed. In the second iteration the sensor was decoupled from the physics loop and sampled at a fixed 10 Hz (every 24 physics steps at 240 Hz), reflecting the real VLP-16 rotation rate and reducing per-frame CPU time by roughly 96 %. Similarly, path planning was initially blocking; the observation that replanning on a 28 × 30 m grid can take several hundred milliseconds led to the introduction of a background planning thread so that the robot continues moving while the new path is computed.

[Figure 4.2 – Component diagram showing module boundaries and interfaces]
Modules: main.py | config.py | simulation/{world, robot} | perception/{lidar, vision, image_collector, localizer} | navigation/{planner, controller, replanner} | virconvnet_train.py

4.2   Simulation Subsystem

The Simulation subsystem is built on top of PyBullet, an open-source rigid-body physics engine with Python bindings. It is responsible for constructing the static warehouse environment, spawning and controlling the robot, and providing the collision geometry against which all sensor ray-casts are resolved.

The warehouse occupies a 28 × 30 m floor area. Six shelf units are arranged in three north–south columns at x = {−8, 0, 8} m; each column contains one unit centred at y = +7 m and one at y = −7 m. A forklift asset is placed at the north-east corner. A variable number of red crate obstacles (0.5 × 0.5 × 0.5 m cubes) can be spawned dynamically at runtime to simulate moving payload. All objects except the crates are assigned concave triangle-mesh collision shapes (GEOM_FORCE_CONCAVE_TRIMESH) so that LiDAR rays penetrate the open shelf frames rather than hitting a bounding-box approximation.

The robot is a differential-drive platform modelled as a rectangular box body (0.5 × 0.35 m footprint) with a mass of 10 kg. Control inputs are a linear velocity v and an angular velocity ω; these are converted to per-wheel speeds using differential-drive kinematics and applied via PyBullet's VELOCITY_CONTROL joint mode. The physics simulation runs at 240 Hz to maintain numerical stability under the high-gain steering controller.

[Figure 4.3 – Warehouse floor plan with shelf positions, forklift location, and robot start pose]
28 m (W) × 30 m (H); Shelf columns at x = −8, 0, +8; Forklift at NE corner; Robot starts at origin

4.3   Perception Subsystem

The Perception subsystem virtualises two sensors: a rotating 3-D LiDAR and a forward-facing RGB-D camera. Both sensors are co-located at the LiDAR mount height above the robot's base link. The subsystem also includes a dataset collection module that synchronises and persists paired LiDAR scans and camera frames to disk, and an obstacle localiser that converts raw sensor observations into a list of detected dynamic obstacles for the navigation module.

The simulated LiDAR is modelled after the Velodyne VLP-16, a 16-channel scanner that produces one full 360° rotation at 10 Hz. Each scan consists of 360 horizontal beams × 16 vertical channels = 5 760 rays per frame. PyBullet's rayTestBatch() function is called in parallel across four threads to resolve all ray intersections simultaneously. The output of each scan is an (N, 4) float32 array of [x, y, z, intensity] coordinates in the sensor frame, together with an (N,) integer array of semantic class labels (0 = background, 1 = shelf, 2 = crate, 3 = forklift) derived by mapping PyBullet body identifiers to class indices.

The camera module uses PyBullet's built-in renderer to capture a 640 × 480 pixel RGB image and a floating-point depth buffer from the robot's forward-facing viewpoint. A separate semantic rendering pass produces a per-pixel class label map at zero additional physics cost, which is used as ground truth for the image segmentation auxiliary loss in VirConvNet.

The projection from the LiDAR sensor frame to the camera image plane follows the standard pinhole model. The sensor frame is defined with +x forward, +y left, and +z up; the camera frame uses OpenCV convention (+x right, +y down, +z forward). The coordinate mapping is:

cx = −ly,    cy = −lz,    cz = lx

and the pixel projection equations are:

u = fx · cx / cz + cx,0 = 240 · (−ly) / lx + 320

v = fy · cy / cz + cy,0 = 240 · (−lz) / lx + 240

where fx = fy = 240.0 px are derived from the simulation's 90° vertical field of view and 480 px image height (f = H / (2 tan(45°)) = 240), and (cx,0, cy,0) = (320, 240) is the principal point at the image centre. A point is considered visible if cz > 0.1 m and (u, v) lies within the 640 × 480 pixel frame. These equations are the inverse of the virtual-point back-projection used in the Training subsystem, described in Section 4.5.

[Figure 4.4 – Perception pipeline: raw ray-cast → point cloud with labels → dataset persistence]

4.4   Navigation Subsystem

The Navigation subsystem is responsible for moving the robot autonomously through the warehouse while reacting to dynamic obstacles detected by the Perception subsystem. It consists of three components: a path planner, a path-following controller, and an obstacle-avoidance module.

The path planner implements the Hybrid A* algorithm, which searches a three-dimensional state space (x, y, θ) and produces paths that are kinematically feasible for a differential-drive robot with a minimum turning radius. A set of motion primitives — seven forward-arc manoeuvres at varying curvatures plus two in-place pivot turns — is used to expand the search frontier. The configuration space is pre-computed by inflating all static obstacle cells by the robot radius (0.3 m), so collision checks reduce to a single grid lookup per primitive.

Path following is handled by a Pure Pursuit–inspired controller that minimises both the heading error (angle between the robot's current orientation and the direction to the next waypoint) and the cross-track error (signed lateral distance from the current path segment). The control law is:

ω = Kheading · eheading + KCTE · eCTE

where Kheading = 3.0 rad/s/rad and KCTE = 1.5 rad/s/m. Linear speed is tapered to zero as the robot approaches the goal.

The obstacle-avoidance module monitors the LiDAR point cloud at 10 Hz and checks whether any newly detected obstacle cell intersects the current planned path. If a collision is forecast, it launches an asynchronous replanning thread so that the robot continues moving on the current path while a new route is computed in the background.

[Figure 4.5 – Navigation subsystem workflow: goal selection → Hybrid A* plan → Pure Pursuit → obstacle check → async replan]

4.5   Training Subsystem

The Training subsystem implements a full offline training pipeline for VirConvNet, a multimodal 3-D semantic segmentation model that fuses sparse LiDAR point clouds with dense camera features. The subsystem is self-contained: given the dataset collected by the Perception subsystem it handles data loading, data augmentation, model construction, mixed-precision training, and per-epoch validation with per-class IoU metrics.

VirConvNet operates in the Bird's Eye View (BEV) representation. The key preprocessing step — virtual point generation — projects LiDAR points onto the image plane, identifies foreground image pixels that lack a corresponding depth return (occluded foreground), and back-projects those pixels into 3-D space using nearby LiDAR geometry, synthesising additional "virtual" points that carry 32-dimensional CNN image features. The enriched point set is then pillarised: the scene volume is discretised into 0.25 × 0.25 m vertical pillars; per-pillar features are aggregated by max-pooling; and a convolutional backbone predicts a per-pillar semantic label.

[Figure 4.6 – VirConvNet architecture: ImageBackbone → VirPillarFeatureNet → BEVBackbone → Segmentation head]
Input: LiDAR scan (.npy) + RGB image (.png) → Output: per-pillar class labels (4 classes)

Because only VirConvNet was trained and evaluated on the collected dataset in this thesis, the subsystem is described exclusively in terms of that model. The dataset contains paired LiDAR scans and camera frames captured at 10 Hz across multiple autonomous traversals of the warehouse, split 80 % for training and 20 % for validation.

Virtual point back-projection. Given a foreground image pixel at (u, v) whose estimated depth is d (borrowed from the nearest occupied LiDAR depth cell), the corresponding 3-D point in the sensor frame is:

cx = (u − cx,0) · d / fx,    cy = (v − cy,0) · d / fy

lx = d,    ly = −cx,    lz = −cy

Per-point pillar feature vector. For a point pi = (x, y, z, r) belonging to pillar Pj with centroid μ = (μx, μy, μz) and centre (xP, yP), the 42-dimensional feature vector is:

fi = [x, y, z, r  |  x−μx, y−μy, z−μz  |  xP, yP  |  φi(1..32)  |  vi]

where φi ∈ ℝ32 is the bilinearly-sampled image feature vector and vi ∈ {0, 1} is the virtual-point flag (1 for back-projected points, 0 for real LiDAR returns).

Combined training loss. The total loss is a weighted sum of the primary 3-D segmentation loss (computed on real LiDAR points) and an auxiliary 2-D image segmentation loss (computed on the ImageBackbone feature map at 1/4 resolution):

ℒ = ℒCE(ŷ3D, yreal) + α · ℒCE(ŷ2D, ymask)

where α = 0.5 is the auxiliary loss weight and ℒCE denotes cross-entropy loss. The auxiliary head is necessary because the numpy-based pillarization step breaks the PyTorch autograd graph between the ImageBackbone and the primary 3-D loss, so without it the ImageBackbone would receive no gradient update.

Class-frequency inverse weighting. To counter class imbalance, each class c is assigned weight:

wc = (1/fc) / Σk(1/fk) · C

where fc is the fraction of training points belonging to class c and C = 4 is the number of classes. The weights are passed to CrossEntropyLoss(weight=...).

Evaluation metric. Model quality is reported as the mean Intersection over Union (mIoU) across all classes:

IoUc = TPc / (TPc + FPc + FNc)      mIoU = (1/C) · Σc IoUc

Classes with no ground-truth points in the validation split (denominator = 0) are excluded from the mIoU average.

5   IMPLEMENTATION DETAILS

5.1   Environment Simulation Module

5.1.1   Environment Assets and Placement

The warehouse world is constructed programmatically in simulation/world.py using only PyBullet primitive shapes and external URDF/OBJ meshes — there is no external scene description file. This choice was made deliberately so that the environment could be regenerated deterministically from a single configuration parameter set, making experiment reproducibility straightforward.

The floor, ceiling, and four perimeter walls are box primitives. Interior dividing walls separate the three shelf columns from the driving corridors. Shelf units are loaded from a custom OBJ mesh with a concave collision shape, which was necessary because the default convex hull approximation caused the LiDAR to treat each shelf unit as a solid rectangular block, masking the internal structure that real robots would see. Switching to GEOM_FORCE_CONCAVE_TRIMESH resolved this at the cost of a longer loading time; since the environment is static, this overhead is paid only once at startup.

Table 5.1 summarises the spatial layout of the key environment elements.

ElementCountPosition(s) (x, y) [m]Notes
Shelf units6(−8, ±7), (0, ±7), (+8, ±7)Concave mesh collision
Forklift1(+10, +11)Concave mesh, static
Dynamic crates0–NRuntime placement0.5 m cube, box collision
Perimeter walls4±14 m (x), ±15 m (y)Box primitives

Obstacle inflation for path planning is performed once during world construction: every grid cell whose centre falls within ROBOT_RADIUS (0.3 m) of any static obstacle surface is marked as occupied. Dynamic crates update a separate obstacle set so that the static inflation does not need to be recomputed when a crate is placed or removed.

Implementation difficulty — concave mesh collision on Windows. PyBullet's concave collision shapes require the mesh to be a closed, manifold surface. Several of the initial OBJ assets had degenerate faces or open edges, which caused PyBullet to silently fall back to a convex hull without emitting a warning. The issue was identified by comparing BEV point clouds between simulation runs and noticing that certain shelf channels were never penetrated by LiDAR rays. The fix involved cleaning the meshes in Blender (Remove Doubles, Recalculate Normals) before re-exporting.

5.1.2   Robot Simulation

The robot is defined programmatically in simulation/robot.py. A base link and two wheel joints are created using createMultiBody(); no URDF file is used. The differential-drive kinematic model converts the commanded linear and angular velocities into individual left and right wheel speeds:

vL = v − ω · L / 2,    vR = v + ω · L / 2

where L = 0.5 m is the axle width. These are applied via setJointMotorControl2(VELOCITY_CONTROL). The robot's pose is read back from PyBullet each step using getBasePositionAndOrientation(), which provides the oracle localisation used by the navigation module.

The maximum linear speed is capped at 1.5 m/s and the maximum angular speed at 3.0 rad/s in the controller before the commands reach the physics engine, preventing the robot from spinning faster than the LiDAR can update its obstacle model.

5.2   Perception Module

5.2.1   LiDAR Sensor Simulation

The simulated LiDAR is implemented in perception/lidar.py. The VLP-16 angular pattern is pre-computed at module load time: 360 azimuth angles uniformly spaced over [0°, 360°) are combined with 16 fixed elevation angles in [−15°, +15°] to produce 5 760 (direction, origin) ray pairs in sensor-local coordinates. These are rotated into world coordinates each frame using the robot's current pose (position + quaternion from PyBullet).

All 5 760 rays are submitted as a single batch to rayTestBatch(numThreads=4), which distributes the workload across four CPU threads inside the PyBullet C++ engine. Each returned hit record contains the body ID and link ID of the struck object, the hit position in world coordinates, and the surface normal. The hit position, together with the robot pose, is used to compute the point in sensor-local [x, y, z] coordinates and a pseudo-intensity value derived from the cosine of the incidence angle.

Semantic labels are assigned by looking up the body ID in a dictionary populated during world construction: 

# perception/lidar.py – semantic label assignment (simplified)
label_map = {
    shelf_body_id:    1,   # shelf
    crate_body_id:    2,   # crate  (updated when crates are spawned/removed)
    forklift_body_id: 3,   # forklift
}

def _label_for_hit(body_id):
    return label_map.get(body_id, 0)  # default: background

The result of one scan is stored as two aligned NumPy arrays: points of shape (N, 4) in float32 (x, y, z, intensity) and labels of shape (N,) in int32. Rays that do not hit any object are excluded from both arrays, so N ≤ 5 760.

Implementation difficulty — label drift when crates are added mid-run. PyBullet assigns body IDs sequentially at creation time, so crates spawned after the label map was initialised were assigned IDs not present in the map and defaulted to label 0 (background), making them invisible to the perception model. The fix was to update the label_map inside the crate-spawning callback, ensuring every newly created body ID is registered before the next LiDAR scan is issued.

A real-time visualisation window (built with OpenCV) displays three panels: a 360×16 range image colour-coded by distance, a bird's-eye view with 5 m concentric range rings and the robot's position, and — when camera collection is active — the RGB frame and the per-pixel segmentation mask. This window was indispensable during debugging, as it made label errors visible immediately without needing to post-process saved files.

[Figure 5.1 – Screenshot of the real-time LiDAR visualisation window: range image (top-left), BEV (top-right), RGB camera (bottom-left), segmentation mask (bottom-right)]

5.2.2   Camera Module Simulation

The camera is implemented in perception/vision.py and perception/image_collector.py. PyBullet's getCameraImage() function is called with a view matrix computed from the robot's current pose and a fixed forward direction. The projection matrix uses a 60° vertical field of view, a 640/480 aspect ratio, and near/far clipping planes at 0.1 m and 20 m respectively.

The function returns four buffers: an 8-bit RGB image, a 32-bit floating-point depth buffer (in OpenGL's non-linear normalised device coordinates), a per-pixel object-ID segmentation map, and a per-pixel link-ID map. The depth buffer is linearised to metric distances using the standard OpenGL inverse projection formula:

dmetric = f · n / (f − (f − n) · dndc)

where n = 0.1 m (near) and f = 20.0 m (far). This linearised depth is used by the obstacle localiser and by VirConvNet's virtual point generation step.

The per-pixel object-ID map produced by PyBullet's segmentation renderer uses the same body IDs as the LiDAR label map, so the same lookup dictionary assigns class labels to pixels with zero additional cost — a deliberate design choice that kept the two sensor pipelines consistent.

5.2.3   Dataset Collection Module

Dataset collection is coordinated by the main loop in main.py. When collection is enabled (controlled by a flag in config.py), every LiDAR scan is paired with a synchronous camera capture: both are triggered from the same simulation step so that the point cloud and image share an identical robot pose. The pairing is enforced by design rather than by timestamp correlation, eliminating any risk of temporal misalignment.

Files are written to training_data/lidar/ and training_data/images/ using a shared global frame counter as the filename stem: 

training_data/
  lidar/
    train/  frame_000000.npy  frame_000001.npy  ...
    val/    frame_000120.npy  ...
  images/
    train/  frame_000000.png  frame_000001.png  ...
    val/    frame_000120.png  ...

The 80/20 train/validation split is decided at collection time using a deterministic modulo rule (frame_id % 5 == 0 → validation), so the split is reproducible without storing a separate index file. Each LiDAR file is a compressed NumPy archive storing both the point array and the label array; each image file is a lossless PNG storing the RGB frame together with a side-channel PNG for the semantic label mask.

Implementation difficulty — DataLoader deadlock on Colab. When the training script was ported to Google Colab for GPU execution, PyTorch's DataLoader with num_workers > 0 caused a deadlock on startup. The root cause is Colab's forked-process model combined with the CUDA context already initialised by the parent process. The fix was to set num_workers=0 on Colab, making data loading synchronous. Because each LiDAR scan is only ~100 KB, the I/O overhead of single-threaded loading was negligible compared to the GPU compute time.

5.3   Navigation Module

5.3.1   Controller

The path-following controller is implemented in navigation/controller.py as the PurePursuitController class. Given the current robot pose (x, y, θ) and a sequence of waypoints produced by the planner, the controller computes a steering command ω and a forward speed v each physics step.

Waypoint advancement uses a parametric progress variable t along each path segment. When t ≥ 1.0 for the current segment, the controller advances to the next one. This is more numerically robust than proximity-based advancement (which can skip short segments on a fast robot or loop on a slow one) because it depends on the signed projection of the robot's position onto the segment direction, which is always well-defined.

The steering law combines heading error and cross-track error: 

# navigation/controller.py – steering law
dx = target.x - robot.x;  dy = target.y - robot.y
e_heading = normalize_angle(atan2(dy, dx) - robot.theta)

# signed lateral distance from the current segment line
e_cte = cross_product(segment_dir, robot_pos - segment_start)

omega = K_HEADING * e_heading + K_CTE * e_cte
omega = clip(omega, -MAX_STEER, +MAX_STEER)

Linear speed is tapered from MAX_SPEED (1.5 m/s) to 0 linearly within LOOKAHEAD_DISTANCE (2.0 m) of the final goal, so the robot decelerates smoothly rather than stopping abruptly.

When a replanned path is spliced in mid-execution via set_path_near(), the controller finds the segment on the new path closest to the robot's current position and starts tracking from there, avoiding the backward lunge that occurred in an earlier version when the new path was always tracked from its beginning.

5.3.2   Hybrid A* Planner

The Hybrid A* planner is implemented in navigation/planner.py as the HybridAStarPlanner class. It searches a discretised 3-D configuration space (x, y, θ) where x and y are quantised to 0.5 m grid cells and θ is quantised into 16 uniform heading bins of 22.5° each. The total state space for the 28 × 30 m warehouse is 56 × 60 × 16 = 53 760 states.

Motion primitives. From each state, 9 successors are generated using pre-computed motion primitives:

  • 7 forward-arc primitives at steering angles {−3, −2, −1, 0, +1, +2, +3} × δmax/3, where δmax = 3.0 rad corresponds to the minimum turning radius at v = MAX_SPEED.
  • 2 pivot-turn primitives (v = 0, ω = ±MAX_STEER) that rotate the robot in place by one heading bin. These are essential for escaping heading deadlocks in narrow corridors where no forward arc leads to a reachable cell.

The pseudocode for the main search loop is: 

function HybridAStar(start, goal):
    OPEN  ← priority queue ordered by f = g + h
    CLOSED ← set of visited discrete states
    push(OPEN, start, f=h(start))

    while OPEN is not empty:
        node ← pop_min(OPEN)
        if discrete(node) in CLOSED: continue
        CLOSED.add(discrete(node))

        if distance(node, goal) < GOAL_TOLERANCE:
            return reconstruct_path(node)

        for each primitive p in PRIMITIVES:
            child ← apply(node, p)
            if collides(child) or discrete(child) in CLOSED:
                continue
            child.g = node.g + arc_length(p)
            child.h = euclidean(child, goal)
            push(OPEN, child, f = child.g + child.h)

    return FAILURE   # goal unreachable

Collision checking calls is_obstacle(grid_x, grid_y), a single array lookup into the pre-inflated occupancy grid. Because the grid is stored as a NumPy boolean array, the lookup is O(1) and cache-friendly.

Dynamic obstacle management. The static obstacle grid is computed once during world construction. Dynamic crates are tracked in a separate Python set dynamic_obstacle_cells. Collision checking is the logical OR of the two: static_grid[x, y] or (x, y) in dynamic_obstacle_cells. This avoids re-inflating the full static grid whenever a crate moves, which would be prohibitively slow.

Implementation difficulty — heading oscillation in long straight corridors. Early testing revealed that the planner sometimes produced paths that zigzagged between adjacent heading bins in straight sections because the heuristic (Euclidean distance) did not penalise heading changes. Adding a small heading-alignment bonus — reducing the heuristic by a constant when the child heading is within one bin of the goal heading — eliminated the zigzag without significantly increasing search time.

5.3.3   Obstacle Avoidance Module

The obstacle avoidance module is distributed across main.py and navigation/replanner.py. Every 24 physics steps (once per LiDAR scan at 10 Hz), the main loop inspects the point cloud for newly occupied grid cells and calls planner.path_is_blocked(current_path) to test whether any of those cells intersect the planned trajectory within a look-ahead horizon of 3.0 m.

If the path is blocked, a background thread is launched to call replan_to_goal(). The main loop continues executing the old path until either the thread returns a new path or the robot reaches the blocked cell, at which point it stops and waits. This two-phase strategy keeps the robot moving in the common case where the obstacle is far enough ahead that replanning completes before the robot arrives. If the direct replan also fails (goal unreachable), the replanner attempts a two-leg detour: it generates a perpendicular offset point away from the obstacle and plans a path through that intermediate waypoint.

When a crate is detected as removed (its LiDAR footprint disappears from the point cloud), remove_dynamic_obstacles() is called to clear the corresponding cells, keeping the obstacle model consistent with the current scene.

Virtual point generation (Cell 6). This is the most novel component and the primary contribution of VirConvNet. The algorithm is detailed below with the actual implementation logic: 

# virconvnet_seg.ipynb – Cell 6 (condensed)
def generate_virtual_points(pts, mask_np, feat_map_np, training=False):
    # 1. Project real LiDAR → sparse depth buffer at 1/4 image resolution
    u_img, v_img, depth, valid = lidar_to_image(pts)
    depth_buf = np.zeros((fH, fW), np.float32)
    for ui, vi, d in zip(u_f[valid], v_f[valid], depth[valid]):
        if depth_buf[vi, ui] == 0 or d < depth_buf[vi, ui]:
            depth_buf[vi, ui] = d     # keep nearest depth per cell

    # 2. Foreground pixels at feature-map resolution with no LiDAR coverage
    msk_small = mask_np[::4, ::4]     # nearest-neighbour downsample
    fg_mask   = (msk_small > 0) & (depth_buf == 0)
    fg_rows, fg_cols = np.where(fg_mask)

    # 3. Nearest occupied depth cell via cKDTree (workers=1 — Colab safety)
    tree = cKDTree(np.stack([occ_rows, occ_cols], axis=1))
    dists, idxs = tree.query(np.stack([fg_rows, fg_cols], axis=1),
                              k=1, workers=1)
    near      = dists <= MAX_DEPTH_SEARCH_PX   # 12 feature pixels ≈ 48 img px
    ref_depth = depth_buf[occ_rows[idxs[near]], occ_cols[idxs[near]]]

    # 4. Subsample and stochastic dropout (VirConvNet §3.2)
    if len(fg_rows) > MAX_VIRTUAL_PTS:          # 1500 cap
        sel = np.random.choice(len(fg_rows), MAX_VIRTUAL_PTS, replace=False)
    if training:
        keep = np.random.rand(len(fg_rows)) > VIRTUAL_DROPOUT  # 0.3

    # 5. Back-project to sensor frame (see Section 4.5 for formula)
    u_virt = fg_cols * 4 + 1.5;  v_virt = fg_rows * 4 + 1.5
    cam_z  = ref_depth
    lx_v   = cam_z;              ly_v = -(u_virt - CX) * cam_z / FX
    lz_v   = -(v_virt - CY) * cam_z / FY

    # 6. Sample 32-D image features at virtual pixel locations
    virt_feat = sample_feat_at_pixels(feat_map_np, fg_cols*4+1.5, fg_rows*4+1.5)
    return virt_pts, virt_feat

Model architecture (Cell 8). The network consists of four stages:

  1. ImageBackbone: two stride-2 Conv2d blocks reduce 640 × 480 RGB to a 32-channel feature map at 160 × 120. Features are bilinearly sampled at each projected LiDAR pixel and at each virtual pixel location.
  2. VirPillarFeatureNet (PFN): a shared Linear(42 → 64) + BatchNorm1d + ReLU applied per point, followed by a per-pillar max-pool, yielding one 64-D descriptor per pillar. This is the PointNet-style set aggregation from PointPillars.
  3. BEVBackbone: three convolutional blocks at full, 1/2, and 1/4 BEV resolution (64→64, 64→128, 128→256 channels), with transposed convolutions to upsample the two downsampled scales back to full resolution, then concatenated to give a (64 + 128 + 128) = 320-channel BEV feature map.
  4. Segmentation head: Conv2d(320 → 128 → 4) with Dropout2d(0.1), producing per-pillar class logits. Point-level predictions are indexed from the BEV logit map using each point's pillar (x, y) coordinate.

The auxiliary head is a single Conv2d(32 → 4) applied to the ImageBackbone output. It provides pixel-level supervision at 120 × 160 resolution and is the only gradient path reaching the image branch, because the numpy pillarization step detaches the PyTorch computation graph from the primary 3-D loss. 

# virconvnet_seg.ipynb – Cell 8 (forward pass summary)
class VirConvNetSeg(nn.Module):
    def encode_images(self, imgs):       # GPU; keeps grad for aux_head
        return self.img_bb(imgs)

    def forward_aux(self, feat_map):     # auxiliary 2-D supervision
        return self.aux_head(feat_map)   # (B, 4, 120, 160)

    def forward_pillars(self, pillars, coords, n_pil):
        pf  = self.pfn(pillars)          # per-pillar 64-D descriptors
        bev = scatter(pf, coords)        # (B, 64, 160, 160) BEV canvas
        return self.head(self.backbone(bev))   # (B, 4, 160, 160)

Training loop (Cells 10–11). One training step proceeds as: (i) encode the RGB batch on GPU with gradient enabled; (ii) compute the auxiliary 2-D loss immediately; (iii) detach the feature maps and run numpy-based pillarization on CPU; (iv) scatter pillars onto the BEV canvas, run the 3-D forward pass, compute the primary loss; (v) backpropagate the combined loss L = L3D + 0.5 · L2D and clip gradients to norm 35.0.

Implementation difficulty 1 — DataLoader and cKDTree worker deadlock on Colab. Both DataLoader(num_workers > 0) and cKDTree.query(workers > 1) launch forked sub-processes. When CUDA is already initialised in the parent process (which happens as soon as the model is moved to GPU), forking corrupts the CUDA context in each child, causing a deadlock on startup with no informative error message. Both were fixed by setting num_workers=0 in the DataLoader and workers=1 in every cKDTree.query() call. Because LiDAR scans average only ~70 KB and the KD-tree candidate sets rarely exceed 1 500 points (capped by MAX_VIRTUAL_PTS), the performance impact was negligible.

Implementation difficulty 2 — broken autograd path through numpy pillarization. The pillarization step converts PyTorch tensors to NumPy arrays, processes them with SciPy/NumPy routines, and returns new tensors. This breaks the autograd computation graph: gradients from the 3-D loss cannot flow back through the pillarizer to the ImageBackbone. As a result, the ImageBackbone would receive no gradient signal and would remain at its random initialisation. The solution was to add the auxiliary segmentation head (Cell 8, forward_aux()) which applies a 1×1 convolution directly to the ImageBackbone output — before detaching — and computes a pixel-wise cross-entropy loss at the feature-map resolution. This auxiliary loss provides the only gradient path that trains the image branch.

Implementation difficulty 3 — class imbalance causing trivial convergence. In the first training run without class weighting, the model converged to predicting background for every point within 5 epochs, achieving ~85 % point accuracy due to the dominance of background returns in warehouse LiDAR scans. The model reported a misleadingly high accuracy while IoU for shelf, crate, and forklift were all 0. Introducing frequency-inverse class weights (Cell 9, estimate_class_weights()) and passing them to CrossEntropyLoss resolved the trivial convergence and the model began correctly predicting foreground classes within the first 10 epochs.

5.5   Other Relevant Modules

5.5.1   Main

The simulation entry point main.py orchestrates all subsystems. Its main responsibilities are: initialising PyBullet and loading the world, selecting an initial random goal, running the 240 Hz physics loop, invoking the LiDAR sensor every 24 steps, launching asynchronous replanning threads when the path is blocked, and writing sensor data to disk when collection is enabled.

An important robustness mechanism is the goal retry loop: if pick_random_goal() fails because all candidate positions are too close to an obstacle, the system waits for the robot to move slightly and tries again after a back-off interval, rather than crashing or selecting an unreachable goal. This situation arises when many dynamic crates are placed simultaneously, temporarily filling the available free space.

Thread safety is enforced by a single threading.Lock that guards write access to the shared path variable. The physics loop holds the lock only while replacing the path reference (a pointer swap), not during path following, so lock contention is negligible.

5.5.2   Configuration File

All tuneable parameters are centralised in config.py. This was a deliberate early design decision: having a single place to change the robot radius, grid resolution, sensor rate, or training dataset path avoids the "magic number" problem where the same constant appears in multiple files with no indication of what it means or where it comes from.
